# OpenAI Integration, Prompting & Context Reference

This document provides a detailed technical reference on how Zizou integrates with the OpenAI API using the Vercel AI SDK, how the system prompt is structured, how context is managed dynamically, and how conversation and tool-calling histories are passed and optimized.

---

## 1. OpenAI API & Vercel AI SDK Calling Details

Zizou uses the **Vercel AI SDK** (`ai` package) to call the OpenAI API. The main execution boundary is in [src/agent/run-turn.ts](file:///c:/Users/Arnv/ZIZOUv1/src/agent/run-turn.ts) via the [streamText()](file:///c:/Users/Arnv/ZIZOUv1/src/agent/run-turn.ts#L262) function.

### Model Resolution & Presets
Models are resolved in [src/sdk/resolve-model.ts](file:///c:/Users/Arnv/ZIZOUv1/src/sdk/resolve-model.ts) via the [resolveModel](file:///c:/Users/Arnv/ZIZOUv1/src/sdk/resolve-model.ts#L43) function. For OpenAI, Zizou supports:
- **Default model**: `gpt-4o-mini` (or custom overrides).
- **Built-in presets** (defined in [src/config/ai-config.ts](file:///c:/Users/Arnv/ZIZOUv1/src/config/ai-config.ts)):
  - **Fast**: `gpt-5-mini` (Reasoning: low, Temp: 0.2, Max tokens: 1024)
  - **Balanced**: `gpt-5-mini` (Reasoning: medium, Temp: 0.2, Max tokens: 2048)
  - **High**: `gpt-5` (Reasoning: high, Temp: 0.1, Max tokens: 4096)
  - **Testing**: `gpt-5-mini` (Reasoning: low, Temp: 0, Max tokens: 512)

### SDK Call Configuration
The call inside [streamText()](file:///c:/Users/Arnv/ZIZOUv1/src/agent/run-turn.ts#L262) is structured as follows:

```typescript
const result = streamText({
  model, // resolved LanguageModel (e.g. openai("gpt-4o"))
  system: systemPrompt, // built by buildSystemPrompt()
  tools, // dictionary of Zizou tools (readFile, writeFile, etc.)
  stopWhen: stepCountIs(maxSteps), // safety cap to prevent loop (default: 15)
  messages: history, // full conversation history (ModelMessage[])
  maxRetries: 0, // disabled to prevent token waste on rate limits/429s
  ...(temperature !== undefined ? { temperature } : {}),
  ...(maxOutputTokens !== undefined ? { maxTokens: maxOutputTokens } : {}),
  ...(providerOptions ? { providerOptions } : {}),
});
```

### Critical Provider-Specific Settings
To guarantee reliable agent behavior, OpenAI calls are configured with specific options:
1. **Disabled Parallel Tool Calls**: 
   ```typescript
   const providerOptions = provider === "openai"
     ? { openai: { parallelToolCalls: false } }
     : undefined;
   ```
   *Why*: OpenAI's default parallel tool execution causes race conditions (e.g., trying to write to a file while simultaneously reading it in the same turn). Forcing sequential tool execution guarantees reliable `read` → `write` → `verify` patterns.
2. **Disabled Retries**:
   *Why*: Setting `maxRetries: 0` surfaces rate limits (HTTP 429) immediately instead of retrying 3 times. This prevents multiplying token consumption on rate-limited payloads, saving user quota.

## 2. System Prompt Structure & Rules

The system prompt is compiled dynamically in [src/context/build-system-prompt.ts](file:///c:/Users/Arnv/ZIZOUv1/src/context/build-system-prompt.ts) via the [buildSystemPrompt()](file:///c:/Users/Arnv/ZIZOUv1/src/context/build-system-prompt.ts#L139) function whenever a session begins. It consists of four distinct layers merged into a single system instruction:

```
BASE_INSTRUCTIONS
      +
SESSION_CONTEXT (OS & Workspace details)
      +
PINNED FILES (Static file injections)
      +
REPO MAP (Workspace structure overview)
```

### Layer 1: BASE_INSTRUCTIONS
A static block of instructions setting up the agent's behavior:
- **Identity**: Sets Zizou's persona as an AI pair programmer.
- **Protocol**: Forces the model to use native function-calling protocols (no plain-text raw JSON blocks).
- **Correct Tool Habits**: Insists on calling `readFile` to fetch exact whitespaces before calling `editFile`.
- **Command Communication**: Instructs the model to briefly narrate what a command does before invoking `runBash` / `runBackground`.

### Layer 2: SESSION_CONTEXT
Dynamic details appended at runtime:
- **Workspace Root**: Injects `process.cwd()`.
- **Environment**: OS (Windows, macOS, Linux) and active shell (PowerShell, bash, zsh).
- **Paths**: Guidelines showing that all relative paths resolve to the workspace root.

### Layer 3: PINNED FILES
Files manually pinned by the user via [addPinnedFile](file:///c:/Users/Arnv/ZIZOUv1/src/context/build-system-prompt.ts#L57). The prompt reads their content and nests them inside:
```
--- PINNED FILES ---
The user has pinned the following files to your permanent context:

File: <absolute-path>
```

### Layer 4: ROLE-AWARE REPO MAP
A structural codebase overview generated by [buildRepoMap](file:///c:/Users/Arnv/ZIZOUv1/src/context/repo-map.ts) in [src/context/repo-map.ts](file:///c:/Users/Arnv/ZIZOUv1/src/context/repo-map.ts). 

To prevent context window bloat under lean settings, Zizou makes **role-aware decisions** about whether to include the repo map:
- **Clarifier** and **Planner** Roles: **Always** receive the repo map. Without it, the planning phase generates references to files that don't exist.
- **Executor** Role:
  - If context budget is set to `light`, the repo map is **omitted** (as the step prompt contains specific target files).
  - If `targetFiles` is empty, the repo map is **omitted**.
  - Under `default` or `max` budgets, the repo map is **included**.

## 3. Context & History Management

Zizou preserves conversation state by forwarding a history array of type `ModelMessage[]` on every turn. 

### Message Types in the History Array
- `role: "user"`: Plain text input from the user (or target-scoped prompt generated for the step executor).
- `role: "assistant"`: The LLM's response, which may include text parts and native tool-call blocks.
- `role: "tool"`: Results generated locally after tool execution, returned back to the model.

### History & Context Optimization
Because tool outputs (like search matches or file lists) can be enormous, the executor cleans history before subsequent turns. The cleaning logic in [src/agent/executor.ts](file:///c:/Users/Arnv/ZIZOUv1/src/agent/executor.ts) via the [cleanHistoryForNextTurn](file:///c:/Users/Arnv/ZIZOUv1/src/agent/executor.ts#L483) function strips large payloads while retaining vital details:

1. **Retains Code Contents**:
   - **`readFile`**: Retains the actual contents read (`cleanedResult.contents = res.contents`) so the model doesn't need to re-read files it has already queried.
   - **`writeFile` & `editFile`**: Retains all input arguments (including full file contents) so the model remembers exactly what code was modified/created.
2. **Minimizes Large Payloads**:
   - **`glob`**: Replaces the full directory tree result with just a simple array of matching file paths.
   - **`grep`**: Replaces detailed line matches with just a unique list of file names containing the hits.
   - **`runBash` & `runBackground`**: Replaces verbose stdout/stderr logs with simple `success: true/false`, a short description, and the task ID.
   - Other tools default to a boolean status and a concise message.

## 4. Native Tool Calling & Fallback Parsing

OpenAI models natively support function/tool calling. However, smaller or less capable models (such as local models called via Ollama or OpenRouter) sometimes output JSON blocks or pseudo-XML tags in their text response instead of sending a structured tool payload.

To handle this, Zizou implements a **Fallback Parser**:
1. **Detection**: If zero native tool calls are triggered but text is returned, Zizou checks the text using regex for pseudo-tags (e.g. `<function/writeFile>...</function>`) or raw JSON blocks.
2. **Execution**: If a valid tool structure is found, Zizou manually executes the tool locally, yields the mock tool-call and tool-result events, and logs the execution.
3. **Morphic Correction**: It wraps the assistant message to resemble a native tool call in the history payload.
4. **Recursion**: It recursively calls [runTurn](file:///c:/Users/Arnv/ZIZOUv1/src/agent/run-turn.ts#L217) with the remaining step count budget to let the model continue its reasoning.
